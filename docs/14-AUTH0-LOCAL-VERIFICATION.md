# Real Auth0 setup and local verification

Status: ready for operator configuration; real Auth0 verification is pending.
Checked against the installed implementation and official documentation on 2026-10-14.

Start here if you do not have Auth0 yet. Nothing needs to be sent to the coding agent. Create the resources below, then copy their values directly into the ignored local files. Never paste client secrets, tokens, passwords, recovery codes or complete environment files into chat, logs, screenshots or source control.

## 1. Create your Auth0 account and development tenant

1. Open the [Auth0 dashboard](https://manage.auth0.com/) and sign up if needed.
2. Create a tenant for **Development**. Choose a unique tenant name and **Europe / EU** region, consistent with ADR-011. The name cannot subsequently be changed. Copy the actual domain shown by Auth0; do not construct it from the tenant name. Auth0 can allocate different regional domain suffixes. See [Create tenants](https://auth0.com/docs/get-started/auth0-overview/create-tenants).
3. Enable MFA on your dashboard/operator account. This protects the dashboard separately from your application's users.
4. Use only development identities here. Confirm pricing, required MFA entitlement and residency before production; this guide does not approve a subscription or legal processing arrangement.

An **Auth0 tenant** is the identity environment for this SaaS. Do not create an Auth0 tenant or Auth0 Organization for each rental company. Rental companies, memberships, roles and platform permissions stay in PostgreSQL. Do not create Auth0 business roles, custom authorization Actions or email-based account-linking rules.

## 2. Register the backend API

Dashboard: **Applications > APIs > Create API**.

| Field | What to enter |
| --- | --- |
| Name | A descriptive development API name of your choice |
| Identifier | A stable unique identifier **you choose and record**. This becomes the audience. It is not generated by this repository, not a client ID, and need not be a reachable HTTP endpoint. Do not use the Auth0 Management API identifier. |
| Signing Algorithm | **RS256** |

Open the new API's **Settings** and save:

- **Access Token Profile: Auth0** (default `access_token` dialect). Do not select RFC 9068 for this implementation: the adapter currently validates `azp`, whereas that profile uses `client_id`. No custom claim Action is necessary. [Token profiles](https://auth0.com/docs/secure/tokens/access-tokens/access-token-profiles)
- **Token Expiration: 600 seconds** as an initial project setting. Keep any browser-flow expiration field at 600 too; implicit flow is not used.
- **Allow Offline Access: On**, so the clients' `offline_access` request can obtain refresh tokens.
- **Enable RBAC: Off**, **Add Permissions in the Access Token: Off**. Application permissions are database grants.
- Do not authorize a machine-to-machine application for this human-login test. Leave agent/delegated authentication and custom token transformations unused.

The API has no callback/logout URLs or client secret to copy. See [API settings](https://auth0.com/docs/get-started/apis/api-settings).

## 3. Register the Next.js application

Dashboard: **Applications > Applications > Create Application**. Choose a descriptive name and **Regular Web Applications**, not Single Page Application.

Open **Settings**:

| Field | Local value |
| --- | --- |
| Allowed Callback URLs | `http://127.0.0.1:3000/auth/callback` |
| Additional temporary Allowed Callback URL | `http://127.0.0.1:43187/callback` — used only for the first operator bootstrap; remove after success |
| Allowed Logout URLs | `http://127.0.0.1:3000` |
| Allowed Web Origins | `http://127.0.0.1:3000` (exact origin; no path) |
| Allowed Origins (CORS) | Leave empty for this server-side web flow; the browser calls the same-origin Next.js bridge |
| Application Login URI | Leave empty for this local test; use the app's Login link |
| Token Endpoint Authentication Method | **Post** (`client_secret_post`), a confidential web client |

Under **Advanced Settings > Grant Types**, enable **Authorization Code** and **Refresh Token**. Do not enable password, implicit or client-credentials grants for this integration. If the tenant exposes API application-access controls, allow this Web application and the Native application below to request this custom API using user authorization; this is not an M2M grant.

Record **Domain**, **Client ID** and **Client Secret** from Settings. The secret belongs only in `apps/web/.env.local`. Use the default tenant domain consistently for this initial development test; do not mix a custom domain and default issuer.

Configure refresh-token rotation and bounded expiration for both applications as below. Save changes. The code uses the [official Next.js SDK](https://github.com/auth0/nextjs-auth0), authorization code/PKCE and an encrypted HTTP-only session. No browser token endpoint is exposed by this app.

## 4. Register the React Native / Expo application

Create a second application with type **Native**. Record its **Client ID**, using the same tenant domain and API identifier. The token endpoint authentication method is **None**. Enable Authorization Code and Refresh Token grants. Never copy a client secret into mobile configuration.

Choose three application identifiers yourself before building:

- A lowercase custom URL scheme (without `://`).
- Your iOS bundle identifier.
- Your Android application package identifier (lowercase).

These are your application choices, not Auth0-generated values. They must match the Expo build configuration. No actual identifiers have been selected in the repository.

Register these **two fully substituted URLs** in both **Allowed Callback URLs** and **Allowed Logout URLs**:

```text
<chosen-scheme>://<copied-auth0-domain>/ios/<chosen-ios-bundle-identifier>/callback
<chosen-scheme>://<copied-auth0-domain>/android/<chosen-android-package>/callback
```

Angle brackets above are explanatory placeholders, not literal values. Native **Allowed Web Origins** and **Allowed Origins (CORS)** can remain empty for this system-browser flow. Do not register Expo Go URLs. Rebuild the native binary after changing scheme/domain/application identifiers. See the [official React Native SDK and Expo plugin](https://github.com/auth0/react-native-auth0).

## 5. Refresh tokens, email and MFA

For **each** Web and Native application, Settings > Refresh Token settings:

- Enable **Refresh Token Rotation**.
- Enable bounded **Maximum Lifetime** and **Idle Lifetime**. Initial development recommendation: maximum **28,800 seconds** (8 hours), idle **3,600 seconds** (1 hour), rotation overlap **5 seconds**. These are project recommendations, not claimed Auth0 defaults; review user experience and production policy later.
- Keep the API's Allow Offline Access enabled. Both clients request `openid profile email offline_access`; bootstrap requests no refresh token.
- Save and obtain a fresh login after changing grant or token settings. Test actual renewal after the 600-second access-token lifetime.

References: [rotation](https://auth0.com/docs/secure/tokens/refresh-tokens/configure-refresh-token-rotation), [expiration](https://auth0.com/docs/secure/tokens/refresh-tokens/configure-refresh-token-expiration).

Dashboard **Authentication > Database**: use an email/password connection for the initial test and enable it for both applications under its Applications tab. Use hosted Universal Login. Permit signup for these development test identities. Do not add social providers or account-linking extensions yet.

Under **Branding > Email Templates**, ensure verification email is enabled. Sign up with email addresses you control, follow the delivered verification links, then sign in again. If necessary, use User Management > Users > the user > send/resend verification email. Confirm **Email Verified** is true. Do not manually toggle the flag to bypass the test. Verify password recovery delivery too. The provider's development email delivery is not a production email setup; configure an approved sender/provider before production. [Email verification](https://auth0.com/docs/manage-users/user-accounts/verify-emails)

For this dedicated development tenant, **Security > Multi-factor Auth**: enable an available authenticator-app factor and use **Always** for the test policy. Enroll both test users and keep recovery codes privately. This is intentionally tenant-wide: the application does not export PlatformAccess to Auth0, and action-specific step-up is not implemented. Confirm the selected subscription supports the required factors/policy; if it does not, record MFA as blocked rather than treating it as verified. Dashboard-account MFA must also be configured independently. [Enable MFA](https://auth0.com/docs/secure/multi-factor-authentication/enable-mfa)

Logout clears the local application session and attempts provider logout. It does not instantly invalidate previously issued API JWTs or necessarily revoke every refresh token. Provider recovery, session revocation and production MFA assurance still require an operational policy.

## 6. Copy values into local files

Preserve the existing database/Redis values in root `.env`. Do not overwrite it with `.env.example`. Create missing web/mobile local files yourself in your editor; Git ignores them. Do not put the web secret into root `.env` or any public variable. The root example groups settings for reference, but each application needs its own locations below.

| File | Variable | Exact source/value |
| --- | --- | --- |
| `.env` | `AUTH0_ISSUER` | `https://` + copied Domain + `/` (trailing slash required) |
| `.env` | `AUTH0_AUDIENCE` | API Settings > Identifier, verbatim |
| `.env` | `AUTH0_ALLOWED_CLIENT_IDS` | Web Client ID, then comma, then Native Client ID |
| `apps/web/.env.local` | `AUTH0_DOMAIN` | Web Settings > Domain, hostname only, no `https://` or `/` |
| `apps/web/.env.local` | `AUTH0_CLIENT_ID` | Web Settings > Client ID |
| `apps/web/.env.local` | `AUTH0_CLIENT_SECRET` | Web Settings > Client Secret; secret |
| `apps/web/.env.local` | `AUTH0_AUDIENCE` | Same API Identifier as root |
| `apps/web/.env.local` | `AUTH0_SECRET` | Locally generated random 32-byte hexadecimal session key; secret |
| `apps/web/.env.local` | `APP_BASE_URL` | `http://127.0.0.1:3000` |
| `apps/web/.env.local` | `API_BASE_URL` | `http://127.0.0.1:3001` |
| `apps/mobile/.env` | `EXPO_PUBLIC_AUTH0_DOMAIN` | Same Domain, hostname only |
| `apps/mobile/.env` | `EXPO_PUBLIC_AUTH0_CLIENT_ID` | **Native** Settings > Client ID |
| `apps/mobile/.env` | `EXPO_PUBLIC_AUTH0_AUDIENCE` | Same API Identifier |
| `apps/mobile/.env` | `EXPO_PUBLIC_AUTH0_SCHEME` | Chosen custom scheme, without `://` |
| `apps/mobile/.env` | `MOBILE_IOS_BUNDLE_IDENTIFIER` | Chosen iOS identifier |
| `apps/mobile/.env` | `MOBILE_ANDROID_PACKAGE` | Chosen Android identifier |
| `apps/mobile/.env` | `EXPO_PUBLIC_API_BASE_URL` | Actual backend address reachable from your device; choose after configuring device networking |

To generate the cookie key without printing it, after creating the web file with the other settings and **without an AUTH0_SECRET line**, run from the repository root:

```powershell
@'
const fs = require('node:fs');
const path = 'apps/web/.env.local';
const contents = fs.readFileSync(path, 'utf8');
if (/^AUTH0_SECRET=/m.test(contents)) throw new Error('AUTH0_SECRET already exists; edit it deliberately');
fs.appendFileSync(path, '\nAUTH0_SECRET=' + require('node:crypto').randomBytes(32).toString('hex') + '\n');
'@ | node
```

Keep local environment files accessible only to trusted workstation users. No Auth0 Management API token, mobile client secret or M2M secret is needed. Restart API/web after editing configuration. API audience, issuer and allowed clients must agree across the files; never use copied sample values as credentials.

Check ignore rules without displaying contents:

```powershell
git check-ignore .env apps/web/.env.local apps/mobile/.env
```

## 7. Start locally and provision the first operator

Run from the repository root, with Docker running:

```powershell
pnpm infra:up
pnpm db:migrate
pnpm db:seed
pnpm build
pnpm --filter @rental/api dev
```

In another terminal run `pnpm --filter @rental/web dev`, then open `http://127.0.0.1:3000` (use that hostname consistently).

1. Click **Login**, sign up for the intended operator's application account, verify its email and complete MFA. Your Auth0 dashboard-owner account does **not** automatically become this application account.
2. The website can show an authenticated Auth0 session while application access is denied. Before bootstrap, `/api/backend/me` returning 401 for this unknown identity is expected.
3. In Auth0 **User Management > Users**, open this application user and copy its exact **User ID** (`user_id`). This is the expected subject; it is not its email and not an application Client ID.
4. Ensure the Web application temporarily allows `http://127.0.0.1:43187/callback`.
5. In a normal interactive local PowerShell terminal run the command below, substituting the copied User ID. Single-quote it, since it can contain `|`. Do not pass a token or password on the command line.

```powershell
pnpm --filter @rental/api bootstrap:platform --subject '<copied Auth0 User ID>' --confirm
```

6. Open the authorization URL the command prints. Sign in as the intended operator, with the configured MFA policy. The command uses fresh authorization code + PKCE and a random state, a loopback-only callback and the confidential Web client's token exchange. It validates the resulting API JWT through the existing adapter and requires matching verified userinfo subject/email. The supplied subject is only an additional expectation, never authentication by itself.
7. Wait for the terminal's success result. Remove the temporary callback URL from Auth0. Return to the website and check application access again. `/api/backend/me` should now include `platform.organization.create` and no organization memberships for a new operator.

This command requires trusted local execution and database credentials; it is not registered in NestJS or exposed through the web app. It checks again transactionally that no PlatformAccess or prior bootstrap audit exists, serializes concurrent attempts, creates or resolves only the exact verified issuer/subject, rejects email-only linking and disabled users, and grants only `platform.organization.create`. Existing membership records are untouched; none are created. It writes `PLATFORM_OPERATOR_BOOTSTRAPPED` and, for a new identity, `IDENTITY_LINKED` in the same transaction. Audit failure rolls everything back. Role names do not confer authority.

An inactive PlatformAccess still blocks a second bootstrap. Do not delete audit records or existing access to rerun it. Additional operators/recovery need a separately reviewed administrative process; there is no reset flag or development bypass. If the database already has a provisioned operator, use that identity instead. No database migration is added by this command.

## 8. Browser verification: operator and second user

Use two separate browser profiles or a private window to keep the two sessions distinct. Prepare a second email address you control. Do not use the operator's email for the first tenant invitation: separation is part of the test.

The current UI supports login, logout, `/me` checks and invitation acceptance. It does **not** yet have an organization-creation form. The following local developer-console helper calls only the existing same-origin authenticated bridge. It never prints credentials or invitation responses. Review the code before executing it; do not disable browser security or paste unrelated console snippets.

In the **operator's** page, define this helper:

```javascript
async function onboardingPost(path, body) {
  const response = await fetch('/api/backend/' + path, {
    method: 'POST',
    headers: { 'content-type': 'application/json' },
    body: JSON.stringify(body),
  });
  if (!response.ok) throw new Error('Request failed: HTTP ' + response.status);
  return response.json();
}
```

Create an organization and its initial invitation. This prompts for your actual name/email and attaches a temporary copy button. The token is held only in the button closure and clipboard; it is not printed to the console or placed in the URL:

```javascript
void (async () => {
  const result = await onboardingPost('platform/organizations', {
    name: prompt('Development organization name'),
    email: prompt('Second user email'),
    defaultCurrency: 'TRY', defaultLanguage: 'en', timezone: 'Europe/Istanbul',
  });
  const button = document.createElement('button');
  button.textContent = 'Copy development invitation';
  button.onclick = async () => {
    await navigator.clipboard.writeText(result.token);
    button.remove();
  };
  document.body.append(button);
})();
```

The currency/language/timezone above are explicit test inputs; adjust if desired. Do not print `result`, export a HAR, enable request-body recording or share Network-panel contents. Invitation responses contain a one-time secret. If clipboard access is blocked, use the browser's ordinary clipboard permission; do not put tokens into console commands. Refreshing before copying loses the token, which cannot be recovered from the database.

1. Check the POST succeeded (201). It creates Organization + configurable tenant role + pending initial invitation, atomically.
2. In the second browser profile, open the app, sign up/login as the invited email, verify email and complete MFA. Unknown application identity `/me` should still be denied before acceptance.
3. Click the temporary copy button in the operator's window; paste into the app's invitation field in the second window and accept. Clear the clipboard afterward. Secure delivery is manual; no invitation email is automatically sent.
4. Check `/api/backend/me` in the second session. Expect the organization and current tenant context with the four administration permissions; expect **no platform permissions**.
5. Check the database records below. There must be one exact issuer/subject ExternalIdentity for the second user, an active Membership and an assigned tenant role. Initial invitations grant `ALL_BRANCHES`; an empty MembershipBranch table is correct for this scope. No Branch is automatically created.
6. Repeat the protected organization-creation request from the second user's session: expect 403. The operator still must not acquire membership simply by creating an organization.
7. Log out each user, confirm application access is unavailable, and log back in. Confirm the same User/ExternalIdentity is resolved and no duplicate Membership is created. Wait over 600 seconds during a session, then check access again to exercise refresh. Test login cancellation, password reset and email verification delivery.

For additional invitations, use `POST /organizations/<actual organization ID>/invitations` through the same bridge in the tenant user's session. Body: `{ email, roleIds, branchScope, branchIds }`. Obtain actual role and branch IDs from the development database, not invented IDs. This call requires both `users.manage` and `roles.manage`. Reuse the copy-button pattern for its response. For revocation use `POST /organizations/<organization ID>/invitations/<invitation ID>/revoke` with `{}`. Before any membership exists, the platform operator can use the corresponding `/platform/organizations/.../revoke` route.

### Inspect persisted results without secrets

Use a trusted local database client connected with the existing development connection. These read-only queries do not select tokens, hashes or credentials:

```sql
SELECT id, name, status FROM "Organization";
SELECT id, name, status FROM "User";
SELECT "userId", issuer, subject FROM "ExternalIdentity";
SELECT id, "userId", active FROM "PlatformAccess";
SELECT "userId", "organizationId", id, status, "branchScope" FROM "Membership";
SELECT "organizationId", id, name, enabled FROM "Role";
SELECT "organizationId", "membershipId", "roleId" FROM "MembershipRole";
SELECT "organizationId", id, name, active FROM "Branch";
SELECT "organizationId", "membershipId", "branchId" FROM "MembershipBranch";
SELECT id, "organizationId", status, "acceptedById", "expiresAt", "acceptedAt"
FROM "OrganizationInvitation";
SELECT "actorUserId", "organizationId", action, "targetType", "targetId", timestamp, source
FROM "AuditEvent" ORDER BY timestamp;
```

Confirm organization/invitation creation, acceptance, membership creation, role assignment and identity linking audits correlate to the actual actors and organization. The bootstrap audit is platform-scoped (`organizationId` null). Never edit audit history.

### Negative invitation checks

Use separate disposable test organizations/invitations; a failed test must not create identity, membership, assignments or success audit rows, or consume the token. Keep tokens in the invitation field/private clipboard, never command-line arguments.

| Case | Setup | Expected |
| --- | --- | --- |
| Wrong user | Valid pending invitation; authenticate with a different verified email | Acceptance denied; invitation still pending |
| Revoked | Revoke while authorized, then attempt acceptance | Denied; no new membership |
| Reused | Accept once, then submit same token again | Denied; exactly one membership/acceptance audit |
| Expired | Wait until its 48-hour expiry, or use a specifically reviewed disposable development database fixture with an elapsed valid lifetime | Denied even if status remains PENDING |
| Suspended organization | Use a disposable organization explicitly suspended by a trusted database operator before acceptance | Denied; token not consumed |
| Unverified email | Sign up but do not verify the invited email | Denied |
| Tenant/platform separation | Second user attempts platform organization creation; operator attempts tenant invitation without membership | Both denied |

There are currently no public organization-suspend, invitation-expiry-edit, role-list, branch-create or membership-management endpoints. Do not invent them or add production bypasses to run these tests. Expired/suspended/disabled-role/disabled-branch/cross-tenant and selected-branch assignment cases are already covered by real PostgreSQL automated fixtures. Live selected-branch verification requires a deliberately prepared development Branch and scoped invitation; it is not established by the initial ALL_BRANCHES flow. Record that test separately if no branch fixture is available.

## 9. Mobile development-build verification

After filling all mobile settings, run:

```powershell
pnpm --filter @rental/mobile exec expo install --check
pnpm --filter @rental/mobile exec expo run:android
```

For iOS use `expo run:ios` on macOS with Xcode, or a separately configured approved build environment. **Expo Go does not support this native Auth0 integration.** JavaScript exports alone are not native verification.

The API binds to `127.0.0.1` by default. For Android USB development, an explicitly configured `adb reverse tcp:3001 tcp:3001` can forward device loopback; verify device/network transport policy allows the selected development endpoint. A physical device otherwise needs a deliberate reachable HTTPS endpoint. Do not expose PostgreSQL/Redis or broadly bind services simply to get login working. No actual mobile API URL is assumed here.

On **both iOS and Android** test:

- System-browser login, correct app callback and cancellation.
- Operator `/me` and second-user tenant `/me`; no cross-use of Web and Native client IDs.
- Invitation acceptance as the intended verified user, and the negative cases above.
- Refresh after access-token expiry; app termination/restart with protected credential storage.
- Logout, local credential clearing, system-browser logout and subsequent login as a different user.
- Expired refresh credentials require reauthentication; no tokens appear in application/device logs.
- Correct role/branch context from the backend and rejection when the organization/membership becomes inactive.
