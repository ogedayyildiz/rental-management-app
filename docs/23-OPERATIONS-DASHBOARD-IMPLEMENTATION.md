# Operations dashboard, notifications and web hardening — Phase 1

## Boundaries

Operations is a read/application module in the NestJS modular monolith. Rental,
Maintenance, Machine and canonical Telemetry records remain authoritative. There
is no second workflow, stored universal machine status, financial projection,
notification worker or provider integration in this phase.

The normal successful Auth0 callback now opens `/dashboard`. `/` preserves the
existing account/invitation entry flow. Production identity verification, token
validation, memberships and platform access are unchanged. Browser automation
continues to use only the isolated E2E harness.

## Dashboard and time semantics

All counts are calculated after tenant and branch scoping. Missing source read
permission omits the corresponding metrics rather than returning unauthorized
values for the browser to hide. The response includes `generatedAt`, organization
timezone and the local dates defining today and the next seven calendar days.
An explicit Refresh fetches current server-derived conditions; this is not a
push/live event feed. Due comparisons use UTC instants; day grouping uses the
organization's IANA timezone, including daylight-saving changes.

| Metric | Definition |
| --- | --- |
| Active rentals | Authorized Rental records in `ACTIVE`; a returned rental awaiting explicit completion is still active. |
| Upcoming dispatches | Rentals with unstarted requested quantity and the earliest outstanding item start in today/the next seven local dates. |
| Returns today | Rentals with an unreturned dispatched assignment and earliest outstanding planned item end on today's local date. |
| Overdue returns | Rentals with an unreturned dispatched assignment whose earliest outstanding item end is earlier than server time. Returned/released assignments do not keep an overdue alert alive. |
| Available now | Additional simultaneous physical units at the current instant. Calls Rental's existing capacity matcher with hypothetical assignments; accounts for unallocated demand, actual assignments, lifecycle/service eligibility and planned workshop periods. Requires both `machines.read` and `rentals.read`. It is not a guarantee for any future rental period. |
| Reserved/rented machines | Active lifecycle machines with the respective Rental-owned rental state. A future reservation can coexist with capacity available right now. |
| Service-restricted machines | Active lifecycle machines in `MAINTENANCE_REQUIRED`, `OUT_OF_SERVICE` or `SERVICE_BLOCKED`; requires Maintenance and Machine read access. |
| Overdue maintenance | Non-completed/non-cancelled work orders whose non-null `dueAt` is earlier than server time, matching Maintenance semantics. |
| Active faults | Canonical active source fault occurrences on installed devices of visible active machines; requires `telemetry.read` and `fault.read`. |
| Offline telemetry machines | Visible active machines with a current installation, known telemetry contact, and canonical connectivity `OFFLINE`. Uninstrumented/unknown machines do not become offline alerts. |

Today/upcoming lists include outstanding dispatches, expected returns, planned
maintenance starts, due work orders and active preventive-plan assignments. Only
active plans and assignments contribute plan attention. No work orders are
generated by the dashboard. Machine service restrictions and in-progress work
orders appear in attention without fabricating new Maintenance states. A generic
"assignment conflict" or "extended" alert is not invented from insufficient
source evidence; the existing Rental detail remains the workflow/history view.

## Canonical telemetry

Machine detail and Operations use the same bulk canonical current-state reader:
fresh/current installation, installed source, health, configured priority,
quality and recorded time determine each signal. No global latest-packet rule
is introduced. `recordedAt` remains distinct from receipt time.

`TELEMETRY_FRESH_SECONDS` remains the existing server setting (default 300).
Offline attention displays last known contact, not proof of a technical fault.
Location/other stale readings remain explicitly last-known. The Machine panel
also displays recent/stale labels and last-update age in minutes. No service,
rental or lifecycle state is changed by freshness or fault alerts.

Each member can set a **display-only** low-SoC threshold, default **20%**. A fresh,
healthy numeric canonical SoC strictly below that threshold produces advisory
attention. Zero is a real reading; absent, unhealthy or stale readings do not
produce low-battery alerts. Threshold zero effectively disables this advisory.
This is not a battery safety limit, dispatch rule or remote command. No generic
high-temperature threshold is assumed.

## Derived notifications and personal interaction state

There is no copied Alert business-event table. Stable notification keys are a
SHA-256 fingerprint of organization, domain, condition, source and occurrence.
Examples: a rental deadline; a work-order due date; a plan assignment's next due
date; the installed contact timestamp; a fault source/code/first-seen/occurrence;
the active service-restriction set. Low-SoC advisory keys additionally use source,
threshold and local observation date to avoid a new unread notification per packet.

The migration adds only:

- `NotificationInteraction(organizationId, membershipId, key, readAt,
  acknowledgedAt, dismissedAt)`.
- `NotificationPreference(organizationId, membershipId, enabled, domains,
  lowSocPercent)`.

Both tables reference Membership using its organization-scoped composite key.
The caller cannot supply a recipient/user/membership ID. There is no email-based
identity resolution. Every read and interaction re-resolves live tenant access;
an interaction must match a currently authorized derived condition. Foreign,
resolved or newly inaccessible keys return 404. Previously stored interaction
rows cannot reveal an inaccessible source after a permission/scope change.

The notification center delivers warning/high-priority attention only. Upcoming
informational items stay on the dashboard/timeline to avoid flooding the inbox.
Preferences mute delivery domains or the whole in-app inbox, not the operational
counts/attention. Read/unread, acknowledge and dismiss are personal and never
resolve a fault, release a service block, close a work order or complete a rental.
Resolved conditions disappear from reads. A changed deadline/fault occurrence
gets a new key and does not inherit an old dismissal. These personal UI mutations
are not sensitive business transitions and do not append business audit events.

`NotificationDelivery` describes the future recipient/content adapter boundary.
There is no external implementation, credential, outbox, email provider, browser
permission prompt, SMS, WhatsApp or push delivery. Future background delivery must
re-authorize the recipient at delivery time. Invitation delivery remains manual.

## Permissions and scope

No broad `dashboard.read` permission or implicit PlatformAccess grant exists.

- Rental reads reuse Rental's responsible-branch **and every historical assigned
  machine branch** predicate.
- Maintenance reads reuse both responsible branch and machine current branch.
- Machine/telemetry reads constrain the current machine branch. Telemetry-only
  members follow alerts to `/machines/:id/telemetry`, which reads the existing
  canonical telemetry API without requesting or granting Machine detail access.
- Plan assignments constrain their machine branch and require Maintenance read.
- Device search follows current installation visibility; uninstalled inventory is
  available only to ALL_BRANCHES members with `device.read`.
- Customer search remains organization-wide under `customers.read`, matching the
  Customer aggregate's existing scope.
- A branch filter narrows authorized data; a selected-branch member requesting an
  unauthorized branch receives 403. Hidden branches never contribute to totals.

There are no amounts, rates, acquisition values, maintenance costs, notes or
commercial terms in the Operations response, even for administrators. Finance
stays a separate permission-controlled analytical screen with ESTIMATE_V1,
currency separation and the existing explicitly estimated labels.

## API and read implementation

All endpoints require authenticated application identity and a valid membership:

| Method / path beneath `/organizations/:organizationId/operations` | Purpose |
| --- | --- |
| `GET /` | Dashboard, attention, bounded timeline/inbox, preferences; optional `branchId`. |
| `GET /search?q=...` | Scoped global search; optional narrowing branch. |
| `PATCH /preferences` | Strict shared preference schema for this membership. |
| `PATCH /notifications/:key` | `READ`, `UNREAD`, `ACKNOWLEDGE` or `DISMISS` on a live authorized key. |

Shared Zod contracts and the API client are used by the real Next.js authenticated
bridge; the bridge's route allowlist and same-origin mutation check are preserved.

The read adapter uses a Repeatable Read transaction and explicit, non-financial
field selections. Owning modules supply scope predicates, the capacity matcher
and the canonical telemetry reader. Telemetry is read in bulk, not one HTTP call
or transaction per machine. Operations performs no writes into source domains.

Source snapshots are capped at 10,000 records per collection and fail rather than
silently returning partial counts. Each presentation list is capped at 200 with
explicit total/limited indicators. Global search returns up to ten matches per
domain with a `limited` flag and no unrestricted export. PostgreSQL `contains`
queries suffice initially; this is not a search-index service. Use branch and
domain workspaces to narrow large operational sets. No distributed cache is added.

## Web shell and workflow hardening

- Consistent permission-aware navigation, active section, account/logout,
  organization selection, language and global search on all domain screens.
- Organization switching destroys the old workspace/drafts, refreshes `/me` and
  navigates to the new organization. It does not silently fall back to another
  tenant when a domain is unavailable. Existing URL organization parameters remain
  supported; last organization is remembered only as a UI selection.
- Concurrent shell/workspace `/me` reads are coalesced with a 15-second presentation
  cache, invalidated on switching/context refresh. Backend authorization always
  comes from fresh database access checks. No token is stored in this cache.
- Quick actions open the appropriate create form with current organization.
  Customer and device search deep links select the actual record.
- EN/TR navigation and page language persist across domain navigation. Search,
  attention and notification labels use shared translation keys.
- Semantic headings, labelled controls, visible keyboard focus, skip link,
  responsive wrapping/navigation and scrollable domain tables. Customer/Machine
  validation summaries receive focus and are associated with invalid fields.
  Inline customer creation preserves Rental and moves/restores focus.
- Safe session/permission/not-found/validation/conflict guidance replaces generic
  failure text in the touched workflows. Known Machine commitment safeguards keep
  their specific explanations.
- Rental detail explicitly explains Return versus Complete: physical return must
  precede completion, and completion does not record payment. No state-machine
  transition was changed.
- Calendar plans are readable under Maintenance read access; edit/activation and
  assignment controls still require `maintenance.plans.manage`. Existing plan
  recurrence/generation behavior remains unchanged.

## Verification and external gates

The following is the Operations milestone. See the [current workspace verification](19-E2E-TESTING.md#current-verification-baseline)
for the expanded suite and latest hosted run; Operations scenarios remain mandatory.

Local verification on 2026-11-19 passed all 167 unit/integration/security tests and
45 Playwright scenarios with no retries or skipped scenarios. Lint, strict TypeScript,
formatting and the full workspace build passed. The additive notification migration
is applied to the local development database; existing business data was preserved.
PostgreSQL/TimescaleDB and Redis remain healthy, and the disposable browser database
and runner lock were cleaned up. The dashboard screenshot was visually reviewed.

Run `pnpm db:migrate`, `pnpm test`, `pnpm test:e2e`, `pnpm lint`,
`pnpm typecheck`, `pnpm format:check`, and `pnpm build`. The existing hosted workflow
runs the same commands with disposable PostgreSQL/TimescaleDB and Redis services.
No permission seed change is needed.

New tests cover scoped counts, source-permission omission, personal interactions,
cross-tenant and composite-FK rejection, timezone/deadline derivation, source keys,
telemetry absence/staleness/SoC, financial omission and actual HTTP contracts.
Playwright exercises the dashboard, quick creation, notification interactions,
simulator freshness/fault clearing, search navigation, EN/TR, small viewports,
errors/empty results, platform/branch/multiple-organization separation and partial
returns, inline-customer focus/draft preservation and telemetry-only source links.
Existing Customer/Machine, full Rental, Maintenance Plan, exports, Finance,
administration and E2E isolation scenarios remain mandatory.

Real provider hardware/cloud access, production ingress, live Auth0/MFA checks,
invitation email delivery and mobile feature development remain external/deferred.
This phase does not claim new verification of those systems.
